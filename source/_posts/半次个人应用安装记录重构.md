# 半次个人应用安装记录重构

## 前言

本文记录一次与AI协作重构个人应用安装记录的过程，核心是沉淀协作中的经验与教训。

重构对象为跨三台设备的应用安装文档（`记应用安装.md`），因文档冗长（数百条记录）、迭代周期长（共8轮会话），过程中出现前后规则不一致、上下文丢失等问题，最终仅完成应用记录格式修正，未统一或优化分类结构，仍保留单文档形式，故称“半次”。

重构采用小批次推进（10~20条/批）、用户可随时介入的方式，完成了 Laptop 01 全量区块、Desktop 01 应用记录、Laptop 02 大部分区块的格式对齐。过程中形成的记法规范附后，供后续维护参考。

## 附录：记法规范

以下规则是本次协作重构过程中逐步明确的，供后续维护参考。

### 单条记录的四层结构

每一条应用记录遵循固定的四层结构：

```
- 应用名
    - 一句说明
    - [状态标记]
    - 时间线
```

**应用名**是无序列表首层。**一句说明**概括作用或场景，不是功能列表。**状态标记**反映当前最终状态，而非中间过程。**时间线**按时间顺序排列事件，备注挂在对应事件下。

该顺序便于快速了解应用用途和当前状态，需要细节时再查看时间线。

### 状态标记

统一使用四种标记：

| 标记 | 含义 |
|------|------|
| `[在用]` | 当前仍在使用 |
| `[已卸载]` | 已卸载 |
| `[停用]` | 安装但未使用 |
| `[仅记录]` | 仅供记录，未安装 |

状态标记反映的是应用当前状态，不是某个中间操作的状态。例如一个应用装了又卸了又装了，最终状态仍是 `[在用]`。

默认策略：只有安装没有卸载记录的条目，默认 `[在用]`；同名应用旧版已删、新版仍在，整体 `[在用]`。

### 时间线的动作词

时间线中每条事件必须以一个动作词开头：

| 动作词 | 含义 |
|--------|------|
| `setup` | 标准安装（安装包、MSI 等） |
| `portable` | 便携式部署（解压即用） |
| `uninstall` | 卸载 |
| `update` | 版本更新 |
| `move` | portable 应用移动位置 |
| `manual` | 手动处理（非安装操作，如手动清缓存、改配置） |
| `npm -g` | npm 全局安装 |
| `pwsh` | PowerShell 脚本安装 |
| `调研` | 调研/比较，尚未安装 |

动作词后面紧跟安装范围 `S` 和路径 `P`：

```
2026-02-03 setup(all users) `D:\Program Files\Git`
2026-03-27 npm -g(unknown) `node 24.14.1`
```

### 安装范围 S

安装范围是时间线中的关键信息。判定规则：

- 路径在 `Program Files` 或 `Program Files (x86)` 下 → `S` 可直接断定为 `all users`，不要写 `unknown`
- 路径在用户目录下（如 `C:\Users\...\AppData`）→ 通常为 `current user`，但非绝对，需结合实际判断
- 路径在自定义位置（如 `D:\Applications\...`）→ 无法从路径推断，写 `unknown` 或根据安装时的记忆填写

同一应用内部，后续事件可简写为 `S同`、`P同`、`S同P同`，但只在当前应用内部回溯，不跨应用。

### 路径 P

路径不杜撰。记不清的写 `unknown`，宁可留空也不猜。npm 全局安装的工具路径写为对应的 Node.js 版本（如 `node 24.14.1`），而不是杜撰一个 `node_modules` 路径。

## 几条容易被忽略的规则

以下规则在重构过程中逐步明确。

### "重装"要拆开

"重装"应拆分为两步：先卸载，再安装。拆开写可以让每一步独立挂备注，避免丢失卸载原因、安装时的新选择等信息。

```
# 错误
2026-03-22 重装 `D:\Applications\BaiduNetdisk`

# 正确
2026-03-22 uninstall(unknown) `D:\Admin\Applications\BaiduNetdisk`
2026-03-22 setup(unknown) `D:\Admin\Applications\Setup\BaiduNetdisk`
    - 此前路径可能是匆忙选择，不符合要求，因此重装
```

### 第三方卸载器写备注，不写进动作

用 Revo Uninstaller 卸载时，动作仍然是 `uninstall`，卸载工具写进备注：

```
2025-12-15 uninstall(all users) `C:\Program Files\Foxit PDF Reader`
    - 使用 Revo Uninstaller 卸载
```

### update 是动作，但"内置更新"不是动作词

`update` 是时间线动作词，表示版本发生了变更。但"内置更新""通过 Microsoft Store 安装"属于备注信息，不要写进动作词本体：

```
# 错误
2026-04-12 内置更新(S同P同) 1.12.4

# 正确
2026-04-12 update(S同P同) 1.12.4
    - 内置更新到"最新"（最新是 1.13.2）
```

### move 仅指 portable 应用移动位置

如果一个应用是"版本替换"——卸载旧版、安装新版——那应该拆成 `uninstall` + `setup`，而不是写 `move`。`move` 仅用于 portable 应用从一个目录移动到另一个目录，版本不变。

### npm -g 安装的工具版本号

npm 全局安装的工具，版本号是工具自身的版本，不是 Node.js 的版本。如果工具版本未知，宁可不写，不要误用 Node.js 版本。

## 重构方法
- 小批次处理（10~20条/批），先确认范围再执行，便于及时修正规则、控制上下文。
- 不跨标题区块修改，避免与手动修正冲突。
- 记录与预期不符时先确认，不擅自覆盖内容。

## 协作教训

与AI协作重构长文档的核心问题：

- **长文档多轮会话的上下文丢失**：8轮会话中，早期约定的规则易在后续轮次中被遗忘，导致前后格式不一致。
- **迭代周期过长**：跨多轮会话的修改，需要反复确认历史规则，增加沟通成本。
- **单文档的维护瓶颈**：将所有设备记录放在同一文档中，长度超过上下文窗口，导致AI处理时遗漏细节。

缓解措施的价值：
- 小批次推进（10~20条/批）：控制单批上下文长度，减少规则遗忘。
- 不跨标题区块修改：避免不同区块的规则混淆。
- 冲突先确认：防止因上下文丢失导致的误改。

若初始按规范记录并拆分文档，可避免此类长周期重构。

## 附：完整记法速查

```
# 单条记录格式
- 应用名
    - 一句说明
    - [状态标记]
    - YYYY-MM-DD 动作(S) `P` [版本]
        - 备注

# 动作词
setup / portable / uninstall / update / move / manual / npm -g / pwsh / 调研 / unknown

# 状态标记
[在用] / [已卸载] / [停用] / [仅记录]

# 简写
S同 = 安装范围同本应用上一条
P同 = 路径同本应用上一条
S同P同 = 两者都同

# S 判定
Program Files / Program Files (x86) → all users
自定义路径 → unknown 或据实填写
```
