> 本文记录的是一次在 Windows 版 Edge 中创建通行密钥的实际体验，并补充相关概念与技术原理。文中涉及的兼容性判断，仅代表当前设备、系统版本和软件环境下的观察结果，不构成通用结论。

# Edge 创建通行密钥的选项差异与跨设备限制

## 一、问题背景

在部分网站中，创建通行密钥时并不会直接提供“扫码保存到手机验证器”的简单入口，而是先交由浏览器或操作系统弹出创建方式。例如在 Windows 版 Edge 中，常见的两个选项是：

1. `Microsoft 密码管理器`
2. `Windows Hello 或外部安全密钥`

这两个选项表面上都能完成通行密钥创建，但其保存位置、可用范围以及跨设备行为并不相同。若事先没有区分清楚，后续使用时很容易产生预期落差。

## 二、两种创建方式的实际差异

### 1. 保存到 Microsoft 密码管理器

选择 `Microsoft 密码管理器` 后，通行密钥会保存到 Edge 账号体系对应的密码管理能力中。

就本文记录的实际使用结果来看，这种方式更接近“保存在 Edge 生态中的浏览器级凭据”：

1. 在登录同一微软账号的 Windows 设备上的 Edge 中，通常可以继续调用和使用。
2. 但在移动设备上，即使使用同一微软账号登录 Edge，也未能直接使用该通行密钥。

因此，至少在本次测试环境下，这一选项更适合作为 Windows 桌面端 Edge 内部的便利能力，而不应默认理解为“自动跨所有 Edge 终端同步可用”。

### 2. 保存到 Windows Hello 或外部安全密钥

选择 `Windows Hello 或外部安全密钥` 后，系统会进一步尝试调用平台认证器或外部认证设备。理论上，这一分支覆盖的范围更广，包括：

1. 当前 Windows 设备上的平台认证器，例如 Windows Hello。
2. 外部安全密钥，例如支持 FIDO2 的 USB / NFC / 蓝牙密钥。
3. 某些支持跨设备通行密钥调用的移动设备。

从设计目标上看，这一路径比“仅保存在 Edge 浏览器内”更偏向系统级或设备级认证能力，因此也更有可能实现跨设备使用。

## 三、一次失败的跨设备尝试记录

在本次测试中，我尝试通过手机完成这一路径中的跨设备认证，但未能成功。

### 1. 测试设备

1. 手机：`Redmi Note 12T Pro`
2. 电脑：分别测试过 `Windows 11 Pro` 和 `Windows 11 Home`
3. 浏览器：Windows 版 Edge

### 2. 已尝试的连接条件

为排除网络或连接问题，我先后尝试了以下组合：

1. 手机与电脑连接同一局域网。
2. 通过 Tailscale 构建虚拟局域网。
3. 手机与电脑开启并互相连接蓝牙。
4. 使用可访问外网的代理。
5. 对上述条件进行组合测试。

### 3. 现象

在扫码后，移动端相关验证器界面始终停留在“正在连接相关设备”一类状态，随后超时退出。无论使用微软相关验证能力还是谷歌侧的验证能力，结果都一致，没有完成后续确认流程。

从结果上看，这并不像单纯的“网络不通”，更像是跨设备认证链路本身未被成功建立。

## 四、一个经验性推测：问题可能不只是网络

基于这次测试，我最初的直觉是：该功能可能需要手机与 Windows 建立更深层的系统级联动，例如某些厂商机型与 Windows 的配套连接能力。

不过，如果从通行密钥和 FIDO 跨设备认证的原理来看，更稳妥的表述应当是：

1. 这类流程通常依赖系统级通行密钥提供方、浏览器实现、蓝牙近距离校验以及设备侧兼容性共同完成。
2. “同一局域网”“能否互相 ping 通”“是否接入 Tailscale”本身，通常都不是决定流程是否成功的充分条件。
3. 即使网络层没有明显问题，只要浏览器、操作系统、手机厂商实现或移动端通行密钥提供方之间缺一环，跨设备流程就可能卡在“正在连接设备”。

因此，就本文记录而言，更合理的结论不是“必须依赖 Windows 的连接手机功能”，而是：在当前设备组合下，跨设备通行密钥链路没有跑通；其原因更可能来自系统级兼容性或实现差异，而不只是普通网络条件。

## 五、密码管理器、认证器与通行密钥分别是什么

这三个概念经常被混用，但实际上并不相同。

### 1. 通行密钥（Passkey）

通行密钥是一种基于公私钥的登录凭据。网站保存公钥，私钥保存在用户设备或受信任的凭据提供方中。登录时不再依赖传统密码，而是通过本地解锁和签名完成认证。

### 2. 认证器（Authenticator）

认证器是实际执行认证动作的主体。它负责持有私钥，并在用户完成本地验证后，对挑战进行签名。

认证器可以是：

1. 平台认证器：如 Windows Hello、Android 系统认证器、iPhone / iPad 的系统认证器。
2. 外部认证器：如 FIDO2 安全密钥。

### 3. 密码管理器（Password Manager）

密码管理器主要负责保存、同步和组织凭据。现代密码管理器除了保存用户名密码，也可能保存通行密钥，并在需要时调用底层认证能力。

因此，密码管理器更偏“凭据容器与同步层”，认证器更偏“实际完成签名的设备或能力”。两者有时集成在一起，但概念上仍应区分。

## 六、这类流程背后的技术原理

### 1. WebAuthn / FIDO2

当前主流通行密钥体系主要建立在 WebAuthn 和 FIDO2 之上。浏览器负责与网站交互，系统或外部设备负责保存密钥并完成签名。

### 2. 跨设备认证不是“扫码登录”的简单变体

手机扫码只是跨设备认证的起点，而不是全部。扫码之后，系统通常还需要建立一条可信通道，以确认“发起请求的电脑”和“持有通行密钥的手机”确实属于同一次近距离认证过程。

在这一过程中，蓝牙近距离证明往往是重要组成部分；实际数据传输则未必完全依赖局域网本身。这也是为什么“同一 Wi-Fi”并不自动等于“一定可用”。

### 3. 代理、Tailscale 和局域网并不必然解决兼容问题

代理主要解决外网访问问题，Tailscale 主要解决网络连通问题，局域网主要解决设备可达性问题。但如果问题出在浏览器实现、系统支持或移动端通行密钥提供方的兼容性上，这些网络层手段通常只能改善环境，不能直接补齐缺失的系统能力。

## 七、结论

对于 Windows 版 Edge 而言，`Microsoft 密码管理器` 与 `Windows Hello 或外部安全密钥` 这两个入口并不只是名称不同，而是对应了两条能力边界明显不同的路径。

前者更接近 Edge 生态内的浏览器级凭据保存；后者则面向更广义的系统级或外部认证能力，也因此承担了更多兼容性变量。

在本文记录的设备环境中，第一种方式可以在 Windows 版 Edge 内部使用，但未能自然延伸到移动端 Edge；第二种方式虽然理论上更适合跨设备，却在实际测试中卡在设备连接阶段，没有完成认证流程。

因此，如果你的目标只是尽快在当前 Windows 设备上完成可用配置，`Microsoft 密码管理器` 往往更直接；如果目标是建立更通用的跨设备通行密钥体系，则应优先关注手机系统、浏览器实现、平台认证器与 FIDO 跨设备支持是否真正匹配，而不要只检查网络是否互通。
