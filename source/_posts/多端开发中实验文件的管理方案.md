> 本文讨论的是“实验性结果文件”在多台开发设备之间的同步方案，重点是在保留本地可访问性的同时，避免污染 Git 仓库和拖慢协作流程。

# 多端开发中实验文件的管理方案

## 一、问题场景

在多端开发环境中，常见的一类需求是：

1. 多台设备之间需要随时查看实验性结果文件。
2. 这些文件数量较多，且往往以大量小文件形式存在。
3. 文件需要保留在项目目录内，以便本地脚本、IDE 或 Coding Agent 可以直接访问。

与此同时，又通常希望满足以下约束：

1. 不污染 Git 提交历史。
2. 不显著增加 Git 的拉取、推送和状态扫描成本。
3. 不因云盘误同步 `.git` 目录而引发卡顿、冲突甚至仓库损坏。

这类需求的核心矛盾在于：实验文件需要“跟项目靠得很近”，但又不应被纳入代码版本控制主通道。

## 二、核心原则

适合这类场景的一条基本原则是：

**代码归 Git，实验产物走专用同步通道。**

也就是说：

1. Git 只管理源代码、配置、文档和必要的元信息。
2. 实验结果、缓存、中间文件、临时输出等内容，应通过独立同步机制处理。

这样做的好处是，代码历史与实验产物可以各自保持边界清晰，彼此不拖累。

## 三、推荐实施方案

### 1. 在项目内创建专用目录

在项目根目录中建立一个专门用于实验文件的目录，例如：

```text
experiments/
```

如果项目有更明确的命名习惯，也可以使用其他名称，例如 `artifacts/`、`runs/`、`scratch/` 等。但无论命名如何，最好满足两个条件：

1. 语义明确，能够一眼区分它与正式源码目录。
2. 路径稳定，便于脚本、工具和多端同步配置长期复用。

### 2. 通过 `.gitignore` 完全忽略该目录

在仓库根目录的 `.gitignore` 中加入：

```gitignore
/experiments/
```

这一步的目标不是“默认不提交”，而是“彻底不进入版本控制视野”。

这样做有几个直接好处：

1. `git status` 不会反复扫描大量实验文件。
2. 提交时不容易误把结果文件带入仓库。
3. 历史记录中不会混入高频、低价值的实验输出。

如果未来实验目录下还会继续分层，例如 `experiments/run-001/`、`experiments/tmp/`，通常也无需额外添加规则，根目录忽略已经足够覆盖。

### 3. 仅同步该目录，不同步整个项目

推荐使用 **Syncthing** 仅同步 `experiments/` 目录本身，而不是同步包含 `.git` 的整个项目根目录。

在多台开发机上，应将同一个 Syncthing 共享文件夹映射到相同的项目相对路径。例如：

```text
<project-root>/experiments/
```

这样做的意义在于：

1. 对本地工具而言，实验文件始终在项目内，访问路径稳定。
2. 对 Git 而言，这些文件始终处于忽略状态，不进入版本管理。
3. 对同步系统而言，数据边界非常清晰，不会误碰源码或仓库元数据。

### 4. 在 Windows 上使用图形界面辅助管理

如果希望降低 Syncthing 的使用门槛，可以在 Windows 上安装 **Syncthing Tray**，并优先选择 `qt6` 版本。

它的作用主要是为 Syncthing 引擎提供桌面端管理界面，包括：

1. 托盘图标与状态查看。
2. 文件夹与设备连接管理。
3. 桌面通知与基础交互。

相较于已经停止维护的 SyncTrayzor，Syncthing Tray 更适合作为当前 Windows 环境下的日常管理入口。

## 四、工具角色划分

| 组件 | 用途 | 关键点 |
| :--- | :--- | :--- |
| **Git + `.gitignore`** | 管理代码与配置，排除实验文件 | 保持仓库历史清晰，避免无关文件进入版本控制 |
| **Syncthing** | 点对点、增量同步实验文件 | 适合大量小文件，不依赖中心化网盘作为主通道 |
| **Syncthing Tray (Qt6)** | Windows 下的图形化管理界面 | 提供更直接的状态管理与通知能力 |

这个划分很重要：

1. Git 解决的是“版本问题”。
2. Syncthing 解决的是“文件分发问题”。
3. GUI 只解决“操作体验问题”。

不要让一个工具承担本不擅长的职责。

## 五、为什么不应直接同步整个项目目录

最需要避免的做法，是使用普通云盘客户端直接同步包含 `.git` 的整个项目根目录。

原因主要有三类：

### 1. `.git` 目录不是普通文档目录

`.git` 内部包含对象库、索引、引用、锁文件等仓库元数据。它的读写过程具有明显的状态性和原子性要求，并不适合被通用云盘工具当作普通文件夹持续监听和同步。

### 2. 极易引发冲突或损坏

当多台设备同时修改、切换分支、提交、拉取或重写索引时，云盘同步可能在不合适的时机复制中间状态，最终表现为：

1. Git 索引异常。
2. 锁文件残留。
3. 对象库不一致。
4. 仓库状态错乱，甚至无法正常提交和检出。

### 3. 性能开销通常很差

Git 仓库本身已经有自己的增量存储与对象管理逻辑。再叠加云盘对大量小文件和元数据变动的实时监听，常常会带来明显卡顿，尤其是在依赖目录、构建目录和实验目录同时变化时。

因此，**不要同步整个项目目录，尤其不要同步 `.git`**，应当视作一条硬性边界。

## 六、路径一致性为什么重要

如果多台设备都要直接消费 `experiments/` 中的结果文件，最好保持项目相对路径一致。

例如，多台设备都采用：

```text
<project-root>/experiments/
```

这样做的好处是：

1. 脚本中的相对路径不需要按设备区分。
2. 配置文件不必为不同机器维护多套目录映射。
3. 工具或 Agent 在不同设备上的访问行为更一致。

当然，项目根目录的绝对路径未必必须完全一致，但至少项目内部的相对布局应尽量稳定。

## 七、如果以后需要版本化实验结果

当实验文件的重要性进一步提高，仅靠“同步但不纳入 Git”可能已经不够。这时可以考虑引入 **DVC** 一类工具。

更合适的分工通常是：

1. Git 仍然只记录代码和元信息。
2. DVC 记录数据版本关系、依赖关系和远程位置。
3. 真正的数据文件托管到对象存储或其他远程存储中。

这种方案比直接把实验结果塞进 Git 更可控，但复杂度也更高，因此更适合在数据确实需要追踪版本时再引入，而不是一开始就强行上全套。

## 八、结论

对于需要在多台设备之间共享实验性结果文件、又希望保持 Git 仓库干净的项目来说，一种较稳妥的做法是：

1. 在项目内建立独立的 `experiments/` 目录。
2. 用 `.gitignore` 将其完全排除在版本控制之外。
3. 用 Syncthing 单独同步该目录。
4. 不让任何云盘工具接触包含 `.git` 的整个项目根目录。

这样既能保证实验文件对本地开发工具可见，又能避免仓库历史、同步性能和 Git 元数据安全性相互牵连。对于个人多端开发和轻量团队协作场景，这是一种边界清晰、维护成本较低的方案。
